# پرامپت اصلاح وضعیت اشتراک بعد از خرید در تریال — ADR-084

در ریپوی Angular موجود HireYar، نمایش وضعیت اشتراک را با رفتار جدید بک‌اند هماهنگ کن. ابتدا AGENTS و کد فعلی سرویس اشتراک، store/cache و کارت داشبورد را بخوان. از ساختار موجود استفاده کن و تغییر را به همین اصلاح محدود نگه دار.

رفتار جدید: اگر سازمان در دوره آزمایشی اشتراک بخرد و خرید توسط سرور تأیید شود، همان لحظه اشتراک پولی فعال و `isTrial=false` می‌شود. روزهای باقی‌مانده هدیه در اعتبار نهایی حفظ می‌شوند. تمدید سه‌ماهه نیز به پایان اعتبار اضافه می‌شود. خریدهای قبلاً تأییدشده هم با نسخه جدید API همین رفتار را دارند. ساخت سفارش Pending یا خرید صرف بسته مصاحبه به معنی خروج از تریال نیست.

منبع وضعیت:

- `GET /api/subscriptions/current` برای Owner و Recruiter.
- `GET /api/dashboard` همان مدل را در `subscription` برمی‌گرداند.
- فیلدهای مرتبط: `hasActiveSubscription`, `isTrial`, `startedAtUtc`, `expiresAtUtc`, `remainingDays`, `remainingInterviews`, `availableInterviews`, `reservedInterviews`, `teamCapacity`, `unlimitedTeam`.

اصلاحات لازم:

1. برای `hasActiveSubscription=true` و `isTrial=true` برچسب «آزمایشی» و برای `hasActiveSubscription=true` و `isTrial=false` برچسب «فعال» نمایش بده. نبود یا انقضای دسترسی را طبق طراحی موجود از `hasActiveSubscription=false` نمایش بده.
2. وضعیت را از تاریخ ثبت‌نام، باقی‌بودن ۴۸ ساعت اول، تاریخ پایان اولیه تریال، localStorage یا وجود سفارش محاسبه نکن. تنها وضعیت تازه سرور ملاک است؛ مقدار false نباید با fallback یا merge اشتباه به مقدار قبلی true برگردد.
3. روزهای باقی‌مانده را مستقیماً از `remainingDays` و تاریخ‌ها را از `startedAtUtc` و `expiresAtUtc` بگیر. بک‌اند UTC می‌دهد؛ تبدیل به تاریخ شمسی/منطقه زمانی طبق ابزار موجود پروژه باشد. روز هدیه و ماه خرید/تمدید را دوباره در فرانت جمع نکن.
4. پس از اینکه جریان موجود خرید، وضعیت Confirmed را از سرور دریافت کرد، cache/store اشتراک و داشبورد را invalidate و پاسخ تازه را دریافت کن. در ورود مجدد یا بازکردن داشبورد نیز اطلاعات تازه خوانده شوند. ایجاد سفارش، بازگشت از صفحه خرید یا نمایش پیام موفقیت به‌تنهایی دلیل فعال‌شدن اشتراک نیست؛ تا تأیید سرور، وضعیت را خوش‌بینانه تغییر نده.
5. هدر و کارت اشتراک و صفحه خرید/تمدید از وضعیت مشترک استفاده کنند تا یک بخش «فعال» و بخش دیگر «آزمایشی» نماند. پاسخ HTTP قدیمی نباید بعد از refresh جدید دوباره store را بازنویسی کند؛ از الگوی فعلی مدیریت درخواست‌های پروژه استفاده کن.
6. Recruiter شمارنده و وضعیت را ببیند، ولی خرید/تمدید همچنان فقط برای Owner باشد. تشخیص isTrial را به فهرست سفارش‌ها وابسته نکن؛ آن API مخصوص Owner است.
7. در مدیریت مشتریان، اگر این بخش در همین ریپو وجود دارد، فیلد وضعیت دریافتی API و subscription تازه را نمایش بده و تریال را از تاریخ ثبت‌نام بازسازی نکن. بعد از تأیید خرید، اطلاعات مشتری/فهرست/آمار مرتبط نیز طبق جریان موجود تازه شوند.

آزمون‌های لازم:

- ثبت‌نام بدون خرید: آزمایشی، ۲ مصاحبه و زمان باقی‌مانده طبق API.
- سفارش Pending و سفارش لغوشده: خروج خودکار از تریال رخ ندهد.
- خرید صرف بسته مصاحبه در تریال: عنوان همچنان آزمایشی باشد.
- تأیید خرید در تریال: عنوان همه بخش‌ها فوراً فعال، شروع برابر مقدار تازه سرور و پایان شامل باقی‌مانده هدیه باشد.
- خرید یک ماه و سپس تمدید سه‌ماهه در همان تریال: فعال بماند؛ روزهای هدیه حذف یا دوباره اضافه نشوند.
- حسابی که قبلاً خرید تأییدشده داشته ولی هنوز در ۴۸ ساعت اول ثبت‌نام است: با دریافت API جدید فعال نمایش داده شود، حتی اگر cache قبلی آزمایشی بوده است.
- `isTrial: false` صریح جای true قبلی را بگیرد؛ پاسخ قدیمی مسابقه درخواست‌ها وضعیت را برنگرداند.
- Owner و Recruiter، بارگذاری دوباره صفحه، نبود اشتراک و انقضای نهایی نیز بررسی شوند.

Build و تست‌های مرتبط فرانت را واقعاً اجرا کن و نتیجه را گزارش بده. قرارداد endpoint و DTO عوض نشده و endpoint جدید یا محاسبه مالی لازم نیست. این رفتار به انتشار نسخه API دارای ADR-084 وابسته است؛ اگر محیط هنوز `isTrial=true` برمی‌گرداند، با حدس محلی آن را false نکن. بک‌اند، migration، push و deploy را در این تسک تغییر نده.
