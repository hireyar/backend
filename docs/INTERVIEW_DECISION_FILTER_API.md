# فیلتر تصمیم انسانی فهرست مصاحبه‌ها — 2026-10-17

`GET /api/interviews` برای Owner و Recruiter سازمان جاری، پارامتر اختیاری و تکرارشونده `humanDecisions` دارد:

| برچسب فرانت | مقدار |
| --- | --- |
| رد شده | `reject` |
| پذیرفته شده | `advance` |
| بررسی توسط کارشناس | `review` |

```http
GET /api/interviews?humanDecisions=reject&page=1&pageSize=20
GET /api/interviews?humanDecisions=advance&humanDecisions=review&statuses=completed&page=1&pageSize=20
```

چند تصمیم با OR و سایر فیلترها با AND ترکیب می‌شوند. مقدار ناشناخته، از جمله `accepted` یا `Advance`، HTTP400 می‌دهد. بدون این پارامتر، فهرست قبلی شامل مصاحبه‌های بدون تصمیم حفظ می‌شود؛ با انتخاب هر گزینه، مصاحبه فاقد تصمیم انسانی کنار گذاشته می‌شود. `items[].humanDecision` همان آخرین تصمیم انسان یا `null` است. `status` همچنان وضعیت انجام مصاحبه است و معنای تازه ندارد. پاسخ همان `{items,total,pageNumber,pageSize}` است؛ فیلتر و total قبل از صفحه‌بندی در PostgreSQL اعمال می‌شوند.

منبع، آخرین ردیف انسانی همین جلسه در `InterviewReviewEntries` است: `RecordedAtUtc` نزولی، سپس `Id` نزولی برای زمان یکسان. هم `POST /api/interviews/{id}/decisions` و هم `POST /api/interviews/{id}/report/review` پوشش دارند. تصمیم قبلی پس از تغییر انتخاب انسان تطبیق ندارد؛ رویداد کارجو، نمره و پیشنهاد AI تصمیم انسانی محسوب نمی‌شوند. قدیمی‌شدن نسخه گزارش، انتخاب انسان را خودکار تغییر یا حذف نمی‌کند؛ وضعیت نیاز به بازبینی مستقل در گزارش باقی است. دعوت مجدد جلسه جدید دارد و تصمیم جلسه قبلی به آن منتقل نمی‌شود. رکورد حذف‌شده و سازمان دیگر در فهرست نیستند. GET هیچ AI یا نوشتنی انجام نمی‌دهد؛ schema و migration تازه ندارد.

Angular در این ریپو نیست. فرانت باید سه گزینه بالا را به فیلتر موجود اضافه کند، مقادیر انتخاب‌شده را با کلید تکراری ارسال کند، هنگام تغییر فیلتر page را1 کند، و items/total پاسخ سرور را مصرف کند. برای «همه» پارامتر حذف شود؛ فیلتر محلی فقط روی صفحه جاری کافی نیست. بعد از ذخیره موفق تصمیم انسانی، فهرست با فیلتر جاری دوباره دریافت شود. داده خالی یا null به تصمیم حدسی تبدیل نشود.
