# اعلان‌های داخل داشبورد — قرارداد جاری

تصمیم تأییدشده کاربر: ASP.NET Core SignalR در همان API و PostgreSQL فعلی؛ بدون سرویس جدا، صف پیام یا Redis. Angular در این مخزن نیست. گیرنده فعلی فقط Owner فعال و تأییدشده همان سازمان است. اعلان‌ها برای همه سازمان‌ها، شامل دمو و تریال و سازمان بدون اشتراک فعال، تولید می‌شوند. شروع/پایان مصاحبه وابسته به اشتراک نیست؛ هشدار کمبود بر اعتبار قابل استفاده و هشدار انقضا فقط بر پایان پوشش مؤثر آینده است. تمدید/override از منبع قطعی فعلی خوانده می‌شود. تاریخچه اعلان قبلی بعد از انقضا حفظ می‌شود.

## رخدادها و مقصد کلیک

| type | زمان تولید | target | interviewId |
|---|---|---|---|
| InterviewStarted | اولین شروع موفق | Interview | شناسه مصاحبه |
| InterviewCompleted | پایان دستی یا خودکار موفق | InterviewReport | شناسه مصاحبه |
| SubscriptionExpiring | ۵ و ۲ روز پیش از پایان پوشش مؤثر | Subscription | null |
| InterviewCreditsLow | اعتبار **قابل استفاده** کمتر از ۲ (۰ یا ۱، با کسر رزروهای معتبر) | InterviewCredits | null |

فرانت target را به مسیر داخلی موجود خودش نگاشت کند؛ آدرس Angular در بک‌اند حدس زده نمی‌شود. InterviewReport باید مستقیم صفحه گزارش همان interviewId را باز کند؛ منبع گزارش موجود `GET /api/interviews/{id}/report` است. پایان مصاحبه به معنی آماده بودن همه تحلیل‌های گزارش نیست؛ وضعیت آماده‌سازی قرارداد گزارش رعایت شود. بازکردن مقصد همچنان کنترل دسترسی مستقل دارد؛ مصاحبه حذف‌شده ممکن است404 باشد.

شروع/پایان و اعلانشان در همان Save/تراکنش ثبت می‌شوند و پس از commit به SignalR خبر داده می‌شود. retry و شروع همزمان اعلان تکراری نمی‌سازند؛ قید unique سازمان/گیرنده/type/sourceKey پشتیبان است. برای تاریخچه پیش از این نسخه اعلان مصاحبه backfill نمی‌شود.

## REST — JWT پنل سازمان، فقط Owner

- `GET /api/notifications?status=all&page=1&pageSize=20`: status اختیاری `all|read|unread`؛ ترتیب جدیدترین بر مبنای createdAtUtc و id؛ page≥1 و pageSize از۱تا۱۰۰. `{items,total,unreadCount,page,pageSize}`. total مربوط به فیلتر جاری، unreadCount مربوط به تمام اعلان‌های گیرنده است.
- هر item: `{id,type,title,target,interviewId,createdAtUtc,readAtUtc}`؛ تاریخ‌ها UTC، شناسه‌ها Guid و `readAtUtc=null` یعنی خوانده‌نشده.
- `GET /api/notifications/unread-count`: `{unreadCount}` برای نشان زنگ.
- `PUT /api/notifications/{id}/read` با `{isRead:true}` یا `{isRead:false}`: پاسخ204. true تکراری زمان خواندن اول را حفظ می‌کند. این تغییر به تمام تب‌های گیرنده خبر داده می‌شود.

افتتاح فهرست یا GET به‌خودی‌خود اعلان‌ها را خوانده‌شده نمی‌کند؛ کلیک روی اعلان را با PUT ثبت کنید. فیلتر خواندن مستقل از نوع رخداد است و برای اضافه‌شدن نوع آینده enum دیتابیسی بسته نداریم. 400: validation_failed / invalid_pagination / invalid_notification_status؛401 نشست نامعتبر؛403 نقش غیرمالک؛404 اعلان غایب یا متعلق به کاربر/سازمان دیگر. پاسخ‌ها no-store هستند؛ org/recipient از ورودی پذیرفته نمی‌شوند.

## اتصال بلادرنگ

Hub: `/hubs/notifications`، احراز هویت JWT فعلی پنل، فقط Owner. گروه از هویت بررسی‌شده سرور ساخته می‌شود و متد عمومی join/send ندارد. رویداد `NotificationsChanged` **بدون آرگومان** است؛ فقط علامت تازه‌شدن است، نه متن یا تعداد. پس از آن شمارنده و در صورت باز بودن dropdown، صفحه فعلی را مجدد بگیرید. این روش نمایش متن را دوباره از کنترل هویت/سازمان عبور می‌دهد. اتصال با پایان عمر JWT بسته می‌شود؛ accessTokenFactory باید توکن معتبر بدهد.

Angular از `@microsoft/signalr`، withAutomaticReconnect و accessTokenFactory استفاده کند؛ callback رویداد را پیش از start ثبت کند، پس از اتصال اولیه و هر reconnect فهرست/شمارنده را دوباره دریافت کند. retry شروع اولیه جدا از reconnect لازم است. پاسخ fetch قدیمی نباید پاسخ جدید را بازنویسی کند؛ درخواست‌ها را coalesce یا cancel کنید. در logout اتصال stop و state پاک شود. تایمر polling فرانت لازم نیست.

قطع اتصال یا restart اعلان ذخیره‌شده را از بین نمی‌برد؛ ارسال زنده best effort است و reload پس از reconnect منبع ترمیم است. بدون outbox/صف و بدون تضمین ارسال در لحظه قطعی اتصال. یک instance API فرض فعلی است؛ انتشار چند instance نیازمند تصمیم جداست.

## بررسی زمان‌دار و جلوگیری از تکرار

Notifications.Enabled=true و Notifications.PollSeconds=60 در appsettings؛ بازه مجاز۱۰تا۳۶۰۰ثانیه. worker داخلی هر دقیقه سازمان‌ها را در صفحه‌های۱۰۰تایی و تراکنش جدا بررسی می‌کند؛ تولید اعلان پیش از اولین دقیقه ممکن است هنوز انجام نشده باشد. شروع/پایان منتظر worker نمی‌مانند. خطای یک سازمان، بقیه را متوقف نمی‌کند.

انقضا از CoverageEnd فعلی، با احتساب تمدید آینده و override معتبر گرفته می‌شود: پنجره ۵روزه `(۲،۵]` روز و پنجره۲روزه `(۰،۲]` روز. برای هر تاریخ پایان/آستانه/گیرنده فقط یک اعلان؛ اگر سرویس پس از ورود به پنجره۲روزه روشن شود فقط هشدار۲روزه ایجاد می‌شود، نه دو هشدار عقب‌افتاده. تمدید تاریخ پایان را تغییر می‌دهد و دوره تازه می‌سازد. پس از انقضا هشداری تولید نمی‌شود.

اعتبار کم در هر دوره پایین‌بودن یک اعلان دارد؛ خواندن آن باعث ارسال دوباره نمی‌شود. وقتی بررسی بعدی اعتبار قابل استفاده≥۲ ببیند، دوره بسته می‌شود؛ پایین‌آمدن دوباره پس از آن اعلان تازه می‌سازد. اگر شارژ و مصرف دوباره هر دو بین دو بررسی رخ بدهند، دوره جدید تشخیص داده نمی‌شود؛ این محدودیت بررسی دقیقه‌ای است.

## امنیت و انتشار

WebSocket/SSE مرورگر JWT را با access_token در query می‌فرستند؛ فقط مسیر خود Hub آن را می‌پذیرد. API لاگ URL در Hosting.Diagnostics و Http.Connections را زیر Warning خاموش می‌کند. در reverse proxy / ingress نیز query این مسیر را حذف یا redact کنید و توکن/URL کامل را در telemetry ثبت نکنید؛ فرانت logging توکن/URL نداشته باشد. فقط HTTPS و CORSهای مجاز فعلی؛ WebSocket upgrade در proxy فعال باشد. JWT فروش و سوپرادمین قابل استفاده نیست.

پیش از API، migration AddDashboardNotifications اعمال شود؛ جدول اعلان، کلید scope ترکیبی کاربر/مصاحبه و indexهای خواندن/dedup اضافه می‌کند. Down دارای تاریخچه اعلان عمداً رد می‌شود. migration در مقصد، UI، push و deploy در این تسک اجرا نشده‌اند.
