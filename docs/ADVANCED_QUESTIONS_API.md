# سؤال‌های موضوعی پکیج پیشرفته

قرارداد backend مطابق `ai_suggest_questions.html`، 2026-10-06. Angular در این ریپو نیست. چینش لیستی/آکاردئونی، حالت بارگذاری، حذف/افزودن در پیش‌نویس و دکمه تأیید کار فرانت است.

## قابلیت و سازگاری

پکیج معمولی همان بانک `questions: string[]` (۵ تا ۳۰ سؤال) را نگه می‌دارد. قالب‌ها و جلسه‌های موجود خودکار تبدیل نمی‌شوند؛ قالب‌های ساده قبلی روی پیشرفته نیز قابل استفاده‌اند. فرانت در جریان تازه پیشرفته، ورودی `topics` را می‌فرستد.

دسترسی بر اساس قابلیت‌های **`advanced_ai_workflow` + `adaptive_questions` + `adaptive_difficulty`** است، نه نام/کد پکیج. هر سه از قبل در قرارداد پیشرفته seed شده‌اند؛ snapshot خریدهای قبلی تغییر نمی‌کند. تولید، ذخیره، دعوت و شروع جلسهٔ موضوعی آن‌ها را بررسی می‌کنند؛ دعوت/شروع قابلیت نوع مصاحبه (`hr_interview` یا `technical_interview`) و `ai_interview` را هم لازم دارد. بانک موضوعی برای هر دو نوع دعوت پیشرفته قابل استفاده است. پس از شروع، قابلیت‌های قرارداد billing همان جلسه ملاک‌اند.

## پیشنهاد AI؛ بدون ذخیره

`POST /api/panel-wizard/question-suggestions`

```json
{ "jobPositionId": "GUID", "topicCount": 7 }
```

مقادیر ۵، ۷، ۱۰ UI همگی مجازند؛ هر عدد صحیح ۵ تا ۱۰ پذیرفته می‌شود. نبود فیلد پیش‌فرض ۷ است؛ `null` یعنی AI بین ۵ تا ۱۰ موضوع مناسب انتخاب کند. عنوان/JD از موقعیت سازمان جاری در سرور خوانده می‌شوند. رکورد حذف‌شده/سازمان دیگر 404، موقعیت آرشیوی 400، نبود قابلیت 403 است.

خروجی:

```json
{
  "jobPositionId": "GUID",
  "topics": [
    { "name": "SQL", "questions": [
      { "level": "easy", "text": "..." },
      { "level": "medium", "text": "..." },
      { "level": "hard", "text": "..." }
    ] }
  ],
  "topicCount": 7,
  "bankQuestionCount": 21,
  "interviewQuestionCount": 14
}
```

نمونه بالا فقط شکل یک موضوع را نشان می‌دهد؛ پاسخ کامل ۵ تا ۱۰ موضوع دارد. فرانت ترتیب سؤال‌ها را از `level` بخواند، نه ترتیب پاسخ AI.

`POST /api/panel-wizard/question-suggestions/topic`

```json
{ "jobPositionId": "GUID", "topicName": "SQL" }
```

همان شکل خروجی، با یک موضوع، سه سؤال در بانک و شمارنده‌های ۱/۳/۲. نام موضوع حفظ می‌شود. فرانت فقط گروه انتخاب‌شده را در پیش‌نویس جایگزین کند؛ گروه‌های دیگر و قالب ذخیره‌شده تغییر نمی‌کنند. تولید مجدد کل بانک همان endpoint اول است.

AI واقعی از adapter موجود NetArz و LLM تنظیم‌شده استفاده می‌کند. JD و نام موضوع داده نامطمئن‌اند و در پیام user جدا از system قرار می‌گیرند. خروجی باید JSON ساختاری معتبر باشد؛ هیچ سؤال نمونه/ساختگی جای شکست provider تحویل داده نمی‌شود. خرابی/timeout/Disabled پاسخ 503 با `question_suggestions_unavailable`، ساختار نامعتبر پاسخ 502 با `question_suggestions_invalid` می‌دهد. لغو درخواست منتشر می‌شود. متن JD/سؤال و کلید در لاگ provider ثبت نمی‌شوند. این عملیات رزرو/تسویه اعتبار مصاحبه ایجاد نمی‌کند؛ مدل billing قبلی همان است.

## تأیید، ذخیره و ویرایش

همان `POST /api/panel-wizard/templates` و `PUT /api/panel-wizard/templates/{id}`؛ ساختار معمولی دست‌نخورده است. در ساختار جدید `questions` را حذف یا `null` کنید و `topics` کامل را بفرستید:

```json
{
  "jobPositionId": "GUID", "title": "مصاحبه تخصصی",
  "interviewType": "specialized", "questions": null,
  "topics": [ { "name": "SQL", "questions": [
    { "level": "easy", "text": "متن تأییدشده کاربر" },
    { "level": "medium", "text": "..." },
    { "level": "hard", "text": "..." }
  ] } ],
  "welcomeMessage": "خوش آمدید", "goodbyeMessage": "متشکریم", "durationMinutes": 60
}
```

نمونه را به ۵ تا ۱۰ موضوع کامل گسترش دهید. موضوع‌ها نام یکتا پس از Trim و بدون حساسیت حروف لاتین، حداکثر ۲۰۰ کاراکتر دارند؛ در هر موضوع دقیقاً یک `easy`، یک `medium` و یک `hard` با متن غیرخالی حداکثر ۲۰۰۰ کاراکتر لازم است. ترتیب موضوع‌ها ترتیب آرایه است. افزودن/حذف/ویرایش موضوع و سؤال در پیش‌نویس آزاد است؛ تأیید نهایی فقط بانک کامل سه‌سطحی را می‌پذیرد. برای حذف یک سؤال، پیش از ذخیره سؤال همان سطح را جایگزین کنید. فرستادن همزمان `questions` و `topics` یا هیچ‌کدام 400 است.

برای PUT همان `{ "template": {...}, "rowVersion": "Base64" }` قبلی؛ نسخه ۱۶بایتی و stale version = 409. مسیر عمومی `PUT /api/interview-templates/{id}` برای قالب موضوعی 400 `use_wizard_for_topic_template` می‌دهد تا ساختار به‌طور ناخواسته از بین نرود. تبدیل صریح موضوعی به ساده با PUT ویزارد و `questions` مجاز است.

GET جزئیات/پاسخ ذخیره افزوده‌های `useTopicQuestions`, `topics`, `interviewQuestionCount` دارد. `questions` قدیمی نیز برای سازگاری به شکل تخت باقی می‌ماند (۱۵ تا ۳۰ سؤال در قالب موضوعی). GET فهرست دارای `useTopicQuestions`, `questionCount` شمار بانک و `interviewQuestionCount` شمار حداکثر پرسش است. مسیر قدیمی دعوت مبتنی بر بانک مهارت، قالب موضوعی را نمی‌پذیرد؛ برای آن از دعوت ویزارد استفاده کنید.

## رفتار جلسه

دعوت همان فرم multipart ویزارد است. گروه‌ها، سؤال‌ها، سطح و نوع ساختار snapshot می‌شوند؛ ویرایش/حذف قالب بعد از دعوت جلسه را تغییر نمی‌دهد. کپی قالب به موقعیت دیگر سازمان نیز گروه‌ها را حفظ می‌کند؛ JD snapshot موقعیت انتخاب‌شده است.

طبق اصلاح صریح کاربر در 2026-10-10، دعوت‌های تازهٔ موضوعی عمومی/تخصصی `ProgressiveTopicQuestions=true` و `MediumFirstTopicQuestions=true` دارند. هر موضوع از متوسط (difficulty=3) شروع می‌شود. اگر پاسخ نهایی متوسط `answerAssessment.correctness >= 0.7` و `confidence >= 0.6` داشته باشد سؤال دوم سخت (5) است؛ برای پاسخ ناقص/ضعیف، اطمینان پایین یا ارزیابی ناموجود، سؤال دوم آسان (1) است. پس از سؤال دوم، مستقل از درستی پاسخ آن، موضوع بسته و موضوع تازه از متوسط آغاز می‌شود. هیچ موضوعی سؤال سوم ندارد. نمره درستی، دقت و کامل‌بودن پاسخ همان سؤال را می‌سنجد؛ وضوح بیان، relevance یا نمره تجمعی مهارت جایگزین آن نیستند.

برای ارزیابی متوسط، shortlist فقط آسان و سخت همان موضوع را دارد؛ پس از ذخیره ارزیابی، سرور شاخه مجاز را اجباری می‌کند. پس از سؤال دوم، AI تخصصی موضوع بعد را از سؤال‌های متوسط مجاز انتخاب می‌کند؛ عمومی ترتیب موضوع‌های قالب را حفظ می‌کند. coverage، adaptive difficulty و sufficient evidence سؤال دوم را حذف یا مصاحبه را زود تمام نمی‌کنند. پاسخ clarify/followUp/redirect سؤال اصلی را عوض نمی‌کند و نمره نهایی ندارد؛ تعامل‌ها جزو دو سؤال اصلی نیستند و ارزیابی نهایی نوبت‌های همان سؤال و اصلاح پاسخ را در نظر می‌گیرد.

حداکثر پرسش جلسه و `interviewQuestionCount` قالب/پیشنهاد، دو برابر تعداد موضوع‌هاست (۱۰ تا ۲۰)، در حالی که بانک همچنان ۱۵ تا ۳۰ سؤال دارد. اگر محدودیت زمان/تکمیل دستی زودتر رخ ندهد، از هر موضوع دو سؤال اصلی پرسیده می‌شود. زمان مصاحبه و محاسبه مصرف اعتبار تغییر نکرده‌اند. نبود/خارج‌بودن نمره از محدوده، JSON نامعتبر یا fallback پس از اتمام تلاش‌های provider، نمره حدسی ایجاد نمی‌کند و برای متوسط به آسان همان موضوع می‌رود. retry/recovery پاسخ قبل از تصمیم نهایی همان سؤال را حفظ می‌کند.

دعوت‌های قبلی با `AskOneQuestionPerTopic=true` همچنان یک سؤال در هر موضوع دارند؛ نسخه قبلی `ProgressiveTopicQuestions=true` و `MediumFirstTopicQuestions=false` نیز مسیر آسان ← متوسط ← سخت و سقف ۳×موضوع را حفظ می‌کند. resend سیاست snapshot همان جلسه را حفظ می‌کند؛ برای استفاده از مسیر جدید برای فردی با دعوت قدیمی، دعوت تازه از قالب بسازید. بانک ساده رفتار قبلی را حفظ می‌کند.

## migration و اجرا

`20261006110718_AddAdvancedTopicQuestions` سه ستون گروه/سطح روی InterviewQuestions و دو flag روی قالب/جلسه اضافه می‌کند؛ مقدار legacy = false، difficulty قبلی = 3 و موضوع null. unique سطح در گروه و check محدوده در PostgreSQL اعمال می‌شوند. سؤال/جلسه/خرید تاریخی بازنویسی نمی‌شود.

`20261010075455_AddProgressiveTopicQuestions` flag جدید با پیش‌فرض false و دو عدد nullable (`Correctness`, `AssessmentConfidence`) روی پاسخ اضافه می‌کند. checkها سیاست‌های متضاد، نمره خارج ۰..۱، نمره ناقص و نمره روی پاسخ تعامل/پردازش‌نشده را منع می‌کنند. numeric بدون گردکردن آستانه ذخیره می‌شود. Down اگر جلسه progressive یا ارزیابی ذخیره‌شده وجود داشته باشد برای جلوگیری از حذف تاریخچه رد می‌شود. ابتدا migration مقصد را اجرا کنید، سپس کد جدید را منتشر کنید.

`20261010085424_AddMediumFirstTopicQuestions` پرچم مسیر متوسط و دو سؤال را با default=false اضافه می‌کند؛ جلسه قبلی بازنویسی نمی‌شود. check وابستگی به progressive و سقف زوج ۱۰..۲۰ را کنترل می‌کند. Down در حضور جلسه با سیاست جدید، تغییر رفتار/حذف snapshot را رد می‌کند. این migration نیز پیش از کد مقصد لازم است.

از ریشه پروژه، با اتصال واقعی محیط خود:

```powershell
$env:ConnectionStrings__Default = 'Host=YOUR_HOST;Port=5432;Database=YOUR_DB;Username=YOUR_USER;Password=YOUR_PASSWORD'
dotnet tool restore
dotnet ef database update --project src/HireYar.Infrastructure --startup-project src/HireYar.Api
```

Connection string را با مقادیر مقصد جایگزین کنید و در Git ثبت نکنید. اجرای این migration در مقصد لازم است؛ این نوبت فقط PostgreSQL مستقل محلی و provider جعلی/HTTP handler تست شده‌اند. schema را پیش از انتشار کدی که ستون‌های جدید را می‌خواند ارتقا دهید. هیچ push/deploy یا اتصال AI/پرداخت واقعی انجام نشده است.
