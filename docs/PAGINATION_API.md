# قرارداد صفحه‌بندی و پرامپت فرانت — 2026-10-16

سه GET زیر از این نسخه به جای آرایه، `Page<T>` برمی‌گردانند؛ اتصال فرانت باید همراه نسخه API هماهنگ شود. فیلدهای هر آیتم و قرارداد POST/PUT تغییر نکرده‌اند. migration لازم نیست.

| GET | دسترسی | ترتیب ثابت |
|---|---|---|
| `/api/job-positions/{positionId}/question-bank` | Owner/Recruiter سازمان جاری | CreatedAtUtc سپس Id، صعودی |
| `/api/admin/pricing/packages` | نشست مستقل SystemAdmin | SortOrder سپس Id، صعودی |
| `/api/admin/pricing/ai-credit-packages` | نشست مستقل SystemAdmin | SortOrder سپس Id، صعودی |

Query: `page=1&pageSize=20`؛ صفحه از ۱، اندازه ۱ تا ۱۰۰. ورودی نامعتبر HTTP400؛ صفحه پس از آخر HTTP200 با items خالی و total واقعی. Count و Skip/Take در PostgreSQL اجرا می‌شوند؛ فهرست مدیریتی فعال/غیرفعال و عمومی/خصوصی را شامل می‌شود. بانک سؤال فقط موقعیت همان سازمان را می‌خواند؛ موقعیت حذف‌شده، ناموجود یا سازمان دیگر 404 است. فیلتر/مرتب‌سازی جدیدی اضافه نشده است.

```json
{ "items": [], "total": 105, "pageNumber": 2, "pageSize": 100 }
```

فهرست‌های زیر همین قرارداد را از قبل دارند و دست‌نخورده‌اند:

| GET | محل داده صفحه | فیلترهای موجود |
|---|---|---|
| `/api/job-positions` | ریشه پاسخ | search، status |
| `/api/interview-templates` | ریشه پاسخ | jobPositionId |
| `/api/interviews` | ریشه پاسخ | search، jobPositionId، statuses، invitedFromUtc/ToUtc، completedFromUtc/ToUtc |
| `/api/team/members` | ریشه پاسخ | — |
| `/api/team/invitations` | ریشه پاسخ | — |
| `/api/billing/payments` | ریشه پاسخ | — |
| `/api/billing/purchases` | ریشه پاسخ | — |
| `/api/billing/ai-credit/transactions` | ریشه پاسخ | — |
| `/api/billing/ai-usage` | ریشه پاسخ | — |
| `/api/billing/financial-history` | `transactions` داخل پاسخ؛ totals و updatedAtUtc مستقل‌اند | fromUtc، toUtc، creditType، transactionType |

نام دقیق پارامترهای بازه مصاحبه: `invitedFromUtc`, `invitedToUtc`, `completedFromUtc`, `completedToUtc`. برای statuses چند مقدار، query تکراری بفرستید و مقادیر وضعیت فعلی UI/قرارداد را حفظ کنید.

تیکت‌ها قرارداد مستقل موجود دارند: GET `/api/tickets` و `/api/admin/tickets` با status/priority؛ GET `/{id}/messages` زیر هر دو مسیر. ورودی page/pageSize با پیش‌فرض۱/۲۰، سقف اندازه۵۰ و سقف صفحه۱۰۰۰۰۰؛ خروجی `{items,total,page,pageSize}` است، نه pageNumber. ترتیب فهرست UpdatedAtUtc نزولی سپس Id؛ ترتیب پیام CreatedAtUtc صعودی سپس Id است. API پیام cursor یا «آخرین صفحه» خودکار ندارد. جزئیات بیشتر: [TICKETING_API](TICKETING_API.md).

فهرست تعریف قابلیت‌های سوپرادمین، اشتراک‌های آینده، کاتالوگ عمومی خرید، جزئیات قالب/گزارش/جلسه و خلاصه داشبورد در این درخواست تغییر نکرده‌اند. عمومی `/api/pricing/packages` و `/api/pricing/ai-credit-packages` همچنان `{packages:[...]}` هستند. مصرف‌کننده‌های عمومی و BillingPanel نباید به endpoint مدیریتی مهاجرت کنند.

## پرامپت آماده برای عامل فرانت

در ریپوی Angular، صفحه‌بندی سمت سرور را برای تمام فهرست‌های این قرارداد وصل و صفحه‌بندی‌های موجود را حفظ کن. ابتدا ساختار فعلی، سرویس‌ها، نوع پاسخ‌ها، احراز هویت و کامپوننت paginator پروژه را بررسی کن و همان الگو را ادامه بده؛ طراحی مجدد صفحات لازم نیست.

۱. سه مسیر GET بانک سؤال موقعیت، پکیج‌های اشتراک سوپرادمین و بسته‌های اعتبار AI سوپرادمین دیگر آرایه نیستند: `/api/job-positions/{positionId}/question-bank`، `/api/admin/pricing/packages`، `/api/admin/pricing/ai-credit-packages`. برایشان `page` و `pageSize` بفرست و `{items,total,pageNumber,pageSize}` دریافت کن؛ مدل آیتم و POST/PUT همان قبلی است. پیش‌فرض۱/۲۰، اندازه حداکثر۱۰۰. paginator باید تعداد کل سرور را بگیرد؛ total را از items.length نساز. شمارش رابط از صفر را فقط در مرز UI به صفحه یک‌مبنای API تبدیل کن. در این سه مسیر search/sort جدیدی فرض نکن.

۲. صفحه‌بندی موقعیت‌ها، قالب‌ها، مصاحبه‌ها، اعضای تیم، دعوت اعضا، پرداخت‌ها، خریدها، تراکنش اعتبار و مصرف AI را حفظ و اتصال UI آن‌ها را بررسی کن. مسیرهای دقیق و فیلترها در جدول بالای همین قرارداد هستند؛ خروجی همگی Page<T> است. در financial-history داده و metadata صفحه در response.transactions قرار دارند؛ totals جمع کل فیلترشده سمت سرور است و نباید از رکوردهای صفحه جاری محاسبه شود.

۳. تیکت سازمان و سوپرادمین و پیام‌های هر تیکت را با قرارداد متفاوت `{items,total,page,pageSize}` حفظ/متصل کن؛ سقف pageSize این‌ها۵۰ است. یک adapter در مرز سرویس می‌تواند page را به مدل مشترک داخلی تبدیل کند. برای گفت‌وگو بارگذاری صفحات متوالی یا «پیام‌های قدیمی‌تر» مناسب است؛ ترتیب زمانی، عدم تکرار پیام و تجربه فعلی حفظ شود. همه پیام‌ها را برای pagination محلی یکجا دانلود نکن.

۴. اندازه‌های انتخابی معمول۲۰/۵۰/۱۰۰ و برای تیکت۲۰/۵۰ باشند. تغییر فیلتر، جستجو، موقعیت انتخاب‌شده یا اندازه صفحه، page را به۱ برگرداند. فیلترهای موجود در جابه‌جایی صفحات حفظ شوند. پاسخ درخواست قدیمی نباید پاسخ جدید را overwrite کند؛ از الگوی فعلی لغو درخواست یا switchMap استفاده کن. جستجوی متنی موجود debounce شود. pagination و filter سمت سرور باشند؛ تنها صفحه جاری را محلی برش نزن.

۵. پس از ایجاد/ویرایش/حذف/دعوت/لغو/پاسخ، صفحه مناسب را دوباره از API بخوان و total را تازه کن. در صورت خالی‌شدن آخرین صفحه با total>0، با سقف ceil(total/pageSize) صفحه معتبر را دوباره بگیر؛ برای total=0 حلقه درخواست ایجاد نکن. تغییر موقعیت بانک سؤال state قبلی را پاک کند. loading، empty، error و retry، وضعیت دکمه‌های قبل/بعد و نمایش فارسی شمارنده‌ها مطابق UI فعلی باشند.

۶. احراز هویت معمول و نشست سوپرادمین/هدر کلید ورود موجود را حفظ کن. سازمان یا نقش را به query اضافه نکن. فهرست‌های عمومی خرید همچنان `{packages:[...]}` هستند و مدلشان نباید تغییر کند. قابلیت‌های سوپرادمین و اشتراک‌های آینده در این تغییر صفحه‌بندی نشده‌اند. نیازی به تغییر چاپ گزارش، جزئیات مصاحبه یا خلاصه داشبورد نیست.

۷. تست‌های مناسب UI/service و build واقعی اجرا کن. حالت‌های بیش از۱۰۰رکورد، صفحه آخر ناقص/خالی، total صفر، تغییر فیلتر/اندازه، پاسخ‌های خارج ترتیب، حذف آخرین ردیف، تفاوت page/pageNumber، wrapper تاریخچه مالی و حفظ کاتالوگ عمومی را بررسی کن. نتیجه اجرا و فایل‌های تغییرکرده را گزارش بده؛ خطا را با داده ساختگی یا pagination محلی پنهان نکن. انتشار یا push در این درخواست نیست.
