اصلاح قطعی کاربر 2026-10-22: در فرم تکمیل اطلاعات، دعوت تکی/گروهی و قالب مصاحبه، انتخاب زبان را کلاً حذف کن؛ نه گزینه غیرفعال و نه selector تک‌گزینه‌ای. فعلاً فقط فارسی است. از بدنه درخواست language را حذف کن و برای نمایش از locale ثابت فارسی استفاده کن. موبایل دعوت همچنان اجباری است.

# پرامپت اتصال پنل Angular: اعضا و دسترسی‌ها

روی ریپوی فرانت هایریار و در چارچوب UI موجود کار کن. API مرجع: TEAM_ACCESS_API.md از بک‌اند. HTML invite_admin.html فقط مرجع طراحی است؛ داده‌های نمونه یا JS نمایشی آن را API فرض نکن.

درخواست قطعی کاربر: **شماره موبایل دعوت‌شونده حتماً اجباری بماند؛ ورود او با OTP همان شماره انجام می‌شود.** ایمیل اختیاری است و برای ارسال دعوت‌نامه استفاده می‌شود؛ فرم چندتایی هم به‌ازای هر نفر موبایل می‌خواهد، صرفاً textarea ایمیل کافی نیست.

۱. مدل auth/me را با accessRole و permissions گسترش بده. مجوزها فقط از سرور؛ role قدیمی Owner/Recruiter برای تشخیص مالک و سازگاری است، مرجع دکمه‌ها نیست. بعد هر تغییر نقش/بازگشت فوکوس/ناوبری و پاسخ403، me دوباره خوانده و context تازه شود؛ به localStorage اعتماد نکن. روی403 حلقه refresh نساز. فیلتر منو، route guard و تمام دکمه‌های write از permissions واحد استفاده کنند؛ حالت ممنوع صفحه فارسی403 با لینک داشبورد/خروج داشته باشد. برای نقش غیرفعال، account/logout همچنان قابل دسترسی باشد.

۲. صفحه اعضا: pagination واقعی اعضا و دعوت‌ها، حالت loading/empty/error، نمایش نام/موبایل/نقش/وضعیت؛ selector از GET team/access-roles و توضیح نقش/دسترسی بخش‌ها از GET team/access-sections. هیچ سه‌نقشی را hardcode نکن. دکمه دعوت برای team Write و نمایش صفحه برای team Read. تغییر نقش از PUT members/id/access، لغو/غیرفعال/بازارسال به API مربوط. مالک غیرقابل تغییر است؛ role administrator را غیرمالک نمی‌تواند تخصیص دهد یا تغییر/غیرفعال کند. isAdministrator از کاتالوگ است، مالک‌بودن از role=Owner. UI هم این عملیات را حذف کند؛ سرور همچنان کنترل می‌کند.

۳. مودال دعوت: نام، نام خانوادگی، **موبایل اجباری با09 و۱۱رقم**، ایمیل اختیاری معتبر، نقش انتخاب‌شده اجباری، پیام اختیاری؛ انتخاب‌گر زبان کاملاً حذف شود، محصول فعلاً فقط فارسی است و language در request ارسال نشود. پیش از ارسال ارقام فارسی موبایل بهASCII نرمال شوند. کارت توضیح نقش و برچسب مشاهده/ویرایش/بدون دسترسی پویا باشد. فرم submit در حال ارسال قفل شود. emailDelivery شکست/پیکربندی‌نشده را موفقیت ارسال ایمیل نشان نده؛ بگو دعوت ثبت شده و ارسال ایمیل موفق نبوده/فعال نیست. بدون ایمیل جریان دعوت موبایلی موجود محفوظ است. پس از ارسال لیست تازه شود.

۴. تب چندتایی: جدول نام/نام خانوادگی/موبایل اجباری/ایمیل اختیاری به‌ازای نفر، نقش مشترک یا قابل تعیین؛ زبان انتخابی نداریم و همه دعوت‌ها فارسی‌اند. حداکثر۵۰ورودی به invitations/batch؛ نتیجه هر آیتم مستقل، موفق‌ها علامت بخورند و فقط شکست‌ها قابل اصلاح/تلاش مجدد باشند. ساختار نامعتبر400 قبل از ارسال؛ برای دعوت تکراری409 توضیح خوانا. از ارسال دوباره کل batch بعد timeout خودداری کن و وضعیت را از لیست بخوان.

۵. نقش ناظر فقط نمایش؛ accessCode و interviewUrl در فهرست او null و canResend/canCancel=false هستند؛ دکمه کپی لینک/کد ورود کارجو را برای interviews Read نساز و GET interviews/id/access را صدا نزن چون Write می‌خواهد. دکمه ایجاد/ویرایش/حذف، ارسال مصاحبه، پیشنهاد سؤال، ثبت ارزیابی و تیکت رندر نشوند. مدیر مصاحبه به مصاحبه/قالب/بانک سؤال/گزارش و تیکت دسترسی نوشتن دارد؛ تنظیمات/اشتراک/تیم پیش‌فرض مخفی‌اند. مدیر می‌تواند طبق کاتالوگ جدید مجوز متفاوتی داشته باشد. GETهای سازمان/اشتراک برای ناظر و مدیر پیش‌فرض403 هستند؛ برای نمایش نام سازمان از me استفاده کن و درخواست مالی بی‌مجوز نزن. تیکت ناظر فقط موارد خودش است.

۶. سوپرادمین: صفحه مدیریت نقش‌ها و بخش‌ها با نشست مستقل SystemAdmin، در همان پوسته/ورود موجود. فهرست نقش، ایجاد نقش جدید، ویرایش نام/شرح/فعال بودن و ماتریس بخش None/Read/Write؛ حذف یک بخش از role بهNone تبدیل می‌شود. isAdministrator زمان ایجاد قابل تعیین و بعداً ثابت است؛ نقش دارای دسترسی تنظیمات/اشتراک/تیم باید administrator باشد. sectionCodeها امنیتی و ثابت‌اند؛ نام/شرح/فعال‌بودن بخش قابل ویرایش با PUT sections/code. revision آخرین GET را بفرست؛409 یعنی reload و حفظ تغییرات تایپ‌شده برای حل تعارض. نقش/بخش را hard-delete نکن، غیرفعال کن. مالک سازمان از غیرفعال‌سازی مجوزها قفل نمی‌شود.

۷. route عمومی /team-invitations/:id بساز: شماره موبایل، درخواست OTP و تأیید همان شماره، پذیرش از auth/team-invitations/id/accept. شناسه لینک دسترسی محسوب نمی‌شود. پس از پذیرش me خوانده و به صفحه مجاز برو. شماره اشتباه، OTP نامعتبر، نقش غیرفعال، دعوت لغو/منقضی/قبلاًپذیرفته‌شده حالت مستقل و متن روشن داشته باشند. لینک ایمیل را درlog/analytics ثبت نکن.

۸. ایمیل در بک‌اند ساخته می‌شود؛ فرانت ایمیل یا HTML را نمی‌سازد. theme تیره و فیروزه‌ای مطابق اپ و نمونه؛ برای رابط هم تایپوگرافی/spacing/components فعلی را نگه دار. حالت موبایل، صفحه‌کلید، focus مودال، RTL و toastهای دقیق را بررسی کن. آمار و فیلتر نمونهHTML را از تعداد صفحه فعلی به‌عنوان مجموع سازمان جعل نکن؛ APIهای فعلی دو لیست صفحه‌بندی‌شده‌اند.

تست پذیرش فرانت: مالک/ادمین/مدیر/ناظر، نقش custom، تغییر زنده مجوز بدون logout، مستقیم‌رفتن به route ممنوع، نبود دکمه‌های write برایRead، موبایل اجباری حتی با ایمیل، پذیرشOTP همان شماره، وضعیت واقعی ارسال ایمیل و partial result دعوت گروهی. قبل انتشار، migration و تنظیمSMTP بک‌اند و مسیر پذیرش فرانت هر دو آماده باشند.
