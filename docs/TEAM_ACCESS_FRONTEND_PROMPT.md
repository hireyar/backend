# پرامپت یکپارچه تغییرات فرانت هایریار

روی ریپوی فرانت هایریار، در پوسته و کامپوننت‌های فعلی Angular پیاده‌سازی کن. این متن درخواست واحد نهایی است: دسترسی‌های قابل تنظیم سوپرادمین، دعوت گروهی تا ظرفیت واقعی، و ایمیل اجباری. مرجع قرارداد بک‌اند TEAM_ACCESS_API.md است. فایل invite_admin.html صرفاً مرجع طراحی است؛ اسکریپت‌ها و داده نمونه آن قرارداد API یا دستور اجرایی نیستند. فرانت در ریپوی بک‌اند موجود نیست.

## قواعد قطعی فرم و زبان

محصول فعلاً فقط فارسی و RTL است. انتخاب زبان را از فرم تکمیل اطلاعات، دعوت تکی/گروهی و فرم قالب مصاحبه کاملاً حذف کن؛ selector تک‌گزینه‌ای یا disabled هم نگذار. در درخواست‌ها language نفرست و کار چندزبانه اضافه نکن.

در دعوت تکی و تک‌تک ردیف‌های گروهی، نام، نام خانوادگی، موبایل، ایمیل و نقش لازم‌اند. موبایل هویت ورود است و هرگز حذف یا با ایمیل جایگزین نشود: ۱۱ رقم ASCII مطابق ^09[0-9]{9}$؛ ارقام فارسی/عربی قبل ارسال نرمال شوند. ورود و پذیرش دعوت با OTP همان شماره است. ایمیل اجباری، معتبر و حداکثر۲۵۶کاراکتر است؛ موبایل معتبر بدون ایمیل کافی نیست. نام و نام خانوادگی هرکدام حداکثر۱۰۰ و مجموع با فاصله حداکثر۲۰۰کاراکتر؛ پیام اختیاری حداکثر۲۰۰۰. trim و خطای کنار فیلد، در هر دو حالت تکی/گروهی یکسان باشد.

## سوپرادمین: نقش‌ها و بخش‌ها

از نشست مستقل SystemAdmin و مسیرهای موجود ورود/پوسته سوپرادمین استفاده کن. مالک سازمان یا نقش سازمانی admin، سوپرادمین سراسری نیست.

- GET /api/admin/access/roles
- PUT /api/admin/access/roles با {code,name,description,isActive,isAdministrator,revision,sections:[{code,access}]}
- GET /api/admin/access/sections
- PUT /api/admin/access/sections/{code} با {name,description,isActive,revision}

فهرست نقش، ساخت نقش جدید و ویرایش نام/شرح/وضعیت/برچسب isAdministrator و ماتریس تمام بخش‌ها را بساز. برای **تمام نقش‌های سازمانی از جمله admin، viewer، interview_manager و custom، همه خانه‌های None/Read/Write قابل ویرایش‌اند**. تمام شرط‌های disabled وابسته به نام نقش، isAdministrator یا حساس‌بودن team/settings/subscriptions را حذف کن. محدودیت واگذاری در سازمان، ماتریس سوپرادمین را قفل نمی‌کند. نام نقش مجوز ثابتی تحمیل نمی‌کند.

requiresOwnerAssignment فقط خروجی مشتق‌شده است؛ به PUT نفرست و با آن ویرایشگر سوپرادمین را قفل نکن. code شناسه ثابت است و بعد ایجاد عوض نمی‌شود؛ این محدودیت شناسه با قفل دسترسی فرق دارد. نام نقش حداکثر۱۰۰، شرح۱۰۰۰ و code مطابق [a-z][a-z0-9_]{1,63}. حذف section از sections ارسالی معادل None است؛ کد ناشناس/تکراری نفرست. برای ساخت revision=null و ویرایش revision آخرین GET را بفرست. در409 داده تایپ‌شده را حفظ کن، آخرین کاتالوگ را بخوان و تعارض را به کاربر نشان بده؛ overwrite خودکار نکن.

نام، شرح و فعال‌بودن هر بخش در سوپرادمین قابل ویرایش است. کد بخش و اتصالش به endpoint ثابت‌اند؛ UI ایجاد بخش نمایشیِ بدون API نساز. غیرفعال‌سازی جای حذف تاریخچه است. مالک سازمان مستقل از ماتریس، دسترسی کامل دارد و با غیرفعال کردن نقش admin قفل نمی‌شود.

## مجوزهای پنل سازمان

GET /api/auth/me شامل accessRole و permissions:[{code,access}] است. permissions مؤثر سرور مرجع منو، route guard و دکمه‌هاست؛ غیبت بخش یعنی None، Read فقط خواندن و Write خواندن/نوشتن. به نام نقش، JWT قدیمی یا localStorage اعتماد نکن. role قدیمی Owner/Recruiter فقط برای مالک‌بودن/سازگاری است. پس از تغییر دسترسی، بازگشت فوکوس و403، context مجوز را تازه کن؛ حلقه refresh نساز. حساب و خروج در دسترس بمانند.

بخش‌ها dashboard/jobs/templates/questions/interviews/reports/settings/subscriptions/tickets/team هستند. صفحه تیم Read و عملیات دعوت/تغییر/غیرفعال/لغو/بازارسال Write می‌خواهند. نقش‌ها را از GET /api/team/access-roles و نام/شرح بخش‌ها را از GET /api/team/access-sections بگیر؛ تعداد نقش‌ها را hardcode نکن.

در پنل سازمان مالک تغییر نقش/غیرفعال نمی‌شود. فقط مالک می‌تواند نقش requiresOwnerAssignment=true را واگذار یا عضو/دعوت دارای آن را مدیریت کند. این پرچم از isAdministrator یا هر مجوز غیرNone در team/settings/subscriptions می‌آید. غیرمالکِ دارای team Write فقط نقش غیرحساس با مجوزهای حداکثر برابر مجوز مؤثر خودش را مدیریت می‌کند؛ هم نقش فعلی هدف و هم نقش درخواستی بررسی شوند. سرور مرجع نهایی403 است. این قواعد مربوط به واگذاری در سازمان‌اند؛ سوپرادمین ماتریس تمام نقش‌ها را آزادانه تنظیم می‌کند.

نام viewer مجوز ثابت ندارد. بر اساس permissions فعلی دکمه بساز: برای interviews Read کد/لینک ورود کارجو نشان نده و GET /api/interviews/{id}/access را صدا نزن؛ این endpoint نیازمند Write است. accessCode/interviewUrl در پاسخ Read تهی و canResend/canCancel=false هستند. پیشنهاد سؤال، ارسال مصاحبه، ثبت ارزیابی و ایجاد تیکت هم Write می‌خواهند. درخواست تنظیمات/مالی بدون مجوز نزن؛ نام سازمان را از me بگیر. ناظر پیش‌فرض فقط تیکت‌های خودش را می‌خواند.

## ظرفیت: محدودیت خود فرم، نه فقط زمان ارسال

پیش از باز کردن دعوت تکی یا گروهی، GET /api/team/invitation-capacity را بدون cache بخوان:

```ts
interface TeamInvitationCapacity {
  hasActiveSubscription: boolean;
  teamLimit: number | null;
  activeMembers: number;
  pendingInvitations: number;
  occupiedSlots: number;
  availableSlots: number | null;
  unlimitedTeam: boolean;
  maxBatchSize: number; // 0..50؛ سقف معتبر ردیف‌های فرم
}
```

نمونه: {hasActiveSubscription:true,teamLimit:5,activeMembers:1,pendingInvitations:2,occupiedSlots:3,availableSlots:2,unlimitedTeam:false,maxBatchSize:2}.

activeMembers شامل مالک و اعضای فعال است. pendingInvitations فقط دعوت منتظرِ منقضی‌نشده/لغونشده است. occupiedSlots جمع این دو است. غیرفعال‌ها و دعوت‌های پذیرفته‌شده/لغوشده/منقضی دوباره شمرده نمی‌شوند. مقادیر را از تعداد صفحه فعلی اعضا، اطلاعات کش‌شده اشتراک یا حدس فرانت محاسبه نکن.

**اگر maxBatchSize=2 است، فقط تا۲ ردیف دعوت قابل نمایش/افزودن/انتخاب/ارسال باشد.** اضافه‌کردن ردیف، paste، import، انتخاب گروهی و میانبر صفحه‌کلید همگی همین سقف را رعایت کنند؛ قبل افزودن بیش از سقف، پیام ظرفیت بده و ردیف اضافه نساز. فایل بزرگ را پنهانی ناقص وارد نکن. شمارنده ظرفیت باقی‌مانده و تعداد دعوت درحال‌انتظار را نشان بده.

اگر maxBatchSize=0 است، ردیف خالی پیش‌فرض نساز؛ حالت اتمام ظرفیت یا نبود اشتراک، دکمه افزودن و ارسال غیرفعال و دعوت تکی هم بسته باشد. اگر بیشتر از صفر است یک ردیف اولیه بساز. اشتراک نامحدود availableSlots=null و maxBatchSize=50 دارد؛ سقف فنی۵۰ همچنان معتبر است.

قبل submit ظرفیت را تازه کن. اگر در تب دیگر ظرفیت کم شده، ارسال را متوقف کن و داده‌های تایپ‌شده را برای اصلاح حفظ کن؛ ردیف اضافه قابل ارسال نباشد، خودکار حذف یا زیرمجموعه‌ای ارسال نشود. بعد ایجاد/لغو/پذیرش/غیرفعال‌سازی، بازگشت فوکوس، تغییر اشتراک و409 دوباره ظرفیت را بخوان. هنگام loading/error ظرفیت، امکان افزودن/ارسال نامحدود نده.

## API دعوت و نتیجه‌ها

POST /api/team/invitations نمونه بدنه:

```json
{"mobile":"09123456789","firstName":"نام","lastName":"نام خانوادگی","email":"person@example.test","accessRoleCode":"interview_manager","message":"پیام اختیاری"}
```

موفقیت201 با TeamInvitationDto شامل id/mobile/firstName/lastName/accessRoleCode/email/status/createdAtUtc/expiresAtUtc/emailDelivery است. نقش انتخاب صریح فرم باشد. انتخاب نقش و کارت توضیح مجوزهایش پویا باشند.

POST /api/team/invitations/batch بدنه {"invitations":[همان رکورد دعوت برای هر نفر]}؛ حداقل۱ و حداکثر maxBatchSize جاری. همه ردیف‌ها پیش از ارسال اعتبارسنجی شوند. ایمیل خالی/نامعتبر هر ردیف، کل درخواست را400 و بدون ثبت هیچ دعوتی می‌کند. اگر تعداد از ظرفیت جاری بیشتر شود، کل درخواست409 با team_capacity_exceeded و بدون ثبت هیچ دعوتی رد می‌شود؛ سرور اولین N نفر را خودکار دعوت نمی‌کند. نبود اشتراک فعال403 با active_subscription_required است. هم‌زمانی چند تب در سرور هم کنترل می‌شود.

داخل سقف ظرفیت، پاسخ200 آرایه نتیجه‌های {mobile,invitation,status,errorCode} است؛ status هر ردیف می‌تواند201/400/403/404/409 باشد. موفق‌ها را علامت بزن/از لیست ارسال خارج کن و فقط شکست‌ها قابل اصلاح و تلاش مجدد باشند. پس از timeout لیست دعوت‌ها و ظرفیت را دوباره بخوان؛ کل گروه را کورکورانه تکرار نکن. در409 ظرفیت داده واردشده حفظ شود و وضعیت جدید نمایش داده شود.

emailDelivery=Sent یعنی ارسال SMTP موفق؛ Failed یا NotConfigured یعنی دعوت ثبت شده اما ارسال ایمیل موفق نبوده یا فعال نیست. این حالت‌ها را «ایمیل ارسال شد» نشان نده و برای رفع خطای ایمیل دعوت تکراری نساز. NotRequested در رکوردهای قدیمی/پاسخ فهرست ممکن است دیده شود؛ برای دعوت جدید بدون ایمیل راه‌حل جایگزین نساز. وضعیت ارسال در پاسخ عملیات است، نه تاریخچه قابل اتکای GET.

سایر مسیرها: GET /api/team/members و /api/team/invitations با pagination واقعی؛ PUT /api/team/members/{id}/access با {accessRoleCode} و موفقیت204؛ POST /api/team/members/{id}/deactivate؛ DELETE /api/team/invitations/{id}؛ POST /api/team/invitations/{id}/resend. resend فقط دعوت منتظر معتبر دارای ایمیل و بدون تمدید مهلت۷۲ساعته است.

## پذیرش و ظاهر

route /team-invitations/:id را بساز. شماره موبایل اجباری، POST /api/auth/otp/request با {mobile} و POST /api/auth/team-invitations/{id}/accept با {mobile,code}؛ CSRF/cookie مطابق auth موجود. شناسه لینک به‌تنهایی دسترسی نمی‌دهد. پس از پذیرش me را بخوان و به مسیر مجاز برو. شماره اشتباه، OTP نامعتبر، دعوت منقضی/لغو/قبلاًپذیرفته‌شده و نقش غیرفعال پیام فارسی روشن داشته باشند. لینک دعوت را در log/analytics ثبت نکن.

ایمیل در بک‌اند با قالب فارسی RTL ساده، شیک و رنگ تیره/فیروزه‌ای ساخته می‌شود؛ فرانت HTML ایمیل تولید نمی‌کند. UI از فونت/spacing/component و تم فعلی اپ استفاده کند؛ responsive، دسترسی صفحه‌کلید، focus مودال، loading/empty/error و قفل submit حین ارسال را رعایت کن. آمار نمونه HTML را به‌جای آمار واقعی نمایش نده.

## پذیرش نهایی

- تغییر تمام خانه‌های ماتریس admin/viewer/interview_manager/custom و isAdministrator در سوپرادمین؛ بدون disabled وابسته به نقش؛409 revision با حفظ فرم.
- تغییر زنده مجوز با همان نشست، route ممنوع، Read بدون عمل Write، مالک محفوظ، عدم دسترسی سازمانی به SystemAdmin، محدودیت واگذاری غیرمالک.
- ظرفیت۲ فقط۲ ردیف در افزودن/paste/import؛ ظرفیت۰ بدون ردیف دعوت؛ نامحدود حداکثر۵۰؛ کاهش ظرفیت حین ویرایش بدون حذف داده یا ارسال خودکار زیرمجموعه.
- دعوت منتظر ظرفیت اشغال کند؛ لغو/انقضا/غیرفعال‌سازی ظرفیت را تازه کند؛ پذیرش pending را به active تبدیل کند؛ دو تب ظرفیت را دور نزنند.
- موبایل و ایمیل هر دو در تکی/تمام ردیف‌های گروهی اجباری؛ OTP همان موبایل؛ نبود انتخاب زبان در تکمیل اطلاعات و دعوت‌ها.
- نتیجه جزئی گروه، تکراری409، batch بیش‌ازظرفیت بدون هیچ ثبت، خطای ایمیل بدون حذف دعوت، عدم ارسال دوباره موفق‌ها پس از retry/timeout.

پیش از انتشار، migration بک‌اند 20261022101526_AddOrganizationAccessControl، SMTP و route پذیرش فرانت آماده باشند. تغییرات اخیر ظرفیت/ایمیل/رفع قفل نقش migration جدید نمی‌خواهند. تست و build فرانت را در ریپوی فرانت واقعاً اجرا و نتیجه را گزارش کن.
