# ثبت‌نام مستقل از ورود

قرارداد جاری 2026-10-17 و ADR-063. پنل Angular در مخزن دیگری است. این قرارداد جایگزین ساخت ضمنی حساب در تأیید OTP می‌شود؛ مسیرهای ایمیل/رمز قدیمی بازگردانده نشده‌اند.

## دریافت OTP مشترک

`GET /api/auth/csrf` سپس `POST /api/auth/otp/request` با بدنه `{"mobile":"09123456789"}`. مقدار token پاسخ CSRF در هدر `X-CSRF-TOKEN` و کوکی همان مرورگر ارسال شود. شماره و کد در JSON هستند، نه URL. نمونه‌ها صرفاً ساختگی‌اند.

ارسال پیامک/حالت fixed قبلی، انقضای پنج‌دقیقه، فاصله درخواست ۶۰ثانیه، سقف پنج تلاش غلط و مصرف یک‌باره مشترک حفظ شده‌اند. request فقط کد می‌فرستد و حساب یا سازمان نمی‌سازد.

## ثبت‌نام

`POST /api/auth/register` با CSRF و همان کوکی:

```json
{
  "mobile": "09123456789",
  "code": "123456",
  "email": "person@example.test",
  "firstName": "نام",
  "lastName": "نام خانوادگی",
  "referralCode": "EXAMPLE-REF"
}
```

موبایل ۱۱رقمی ASCII با شروع09، کد۶رقمی، ایمیل معتبر حداکثر۲۵۶، نام و نام خانوادگی هرکدام اجباری/غیرwhitespace و حداکثر۱۰۰کاراکتر ورودی‌اند. نام‌ها Trim و با یک فاصله در FullName موجود ذخیره می‌شوند؛ مجموع نهایی حداکثر۲۰۰. قالب پروفایل قبلی FullName باقی است و نام‌های تاریخی تفکیک یا حدس زده نمی‌شوند.

referralCode اختیاری و حداکثر۶۴کاراکتر ورودی است؛ Trim، مقدار خالی/whitespace/null به null تبدیل می‌شود. متن فقط روی حساب تازه ذخیره می‌شود: اعتبارسنجی معرف، ارتباط با سازمان/حساب دیگر، پاداش یا تغییر اعتبار وجود ندارد. از مقادیر ذخیره‌شده سیستم ریفرال آینده نتیجه‌گیری نکنید.

ایمیل با normalization موجود Identity و قید unique موجود PostgreSQL یکتا است؛ ایمیل تأییدشده تلقی نمی‌شود (`EmailConfirmed=false`) و این تغییر ارسال یا تأیید ایمیل ندارد. ورود همچنان فقط با موبایل/OTP است. حساب‌های قبلی بدون ایمیل الزام تازه برای ورود نمی‌گیرند.

در موفقیت200، Owner/سازمان اولیه، trial/هدیه با تنظیمات موجود، مصرف OTP و نشست در یک تراکنش ایجاد می‌شوند. پاسخ مانند ورود `accessToken` و `expiresAtUtc` دارد؛ refresh فقط در کوکی HttpOnly قبلی است. نقش، سازمان و هدیه از سمت سرور تعیین می‌شوند؛ ورودی ناشناخته/overposting400 است. بعد از موفقیت، `GET /api/auth/me` اطلاعات ایمیل و fullName را برمی‌گرداند؛ CSRF را با Bearer تازه دوباره دریافت کنید.

## ورود حساب موجود

`POST /api/auth/otp/verify` فقط `mobile` و `code` می‌گیرد و حساب جدید نمی‌سازد. حساب موجود Owner/Recruiter با OTP معتبر همان نشست قبلی را می‌گیرد؛ trial یا هدیه تازه داده نمی‌شود. برای شماره تازه با OTP صحیح،409 و code=`registration_required` برمی‌گردد؛ فرانت به فرم ثبت‌نام هدایت کند. OTP در این خطای مسیر مصرف نمی‌شود و تا زمان اعتبار با اطلاعات کامل برای register قابل استفاده است. کد نامعتبر/منقضی/مصرف‌شده همچنان401 است؛ وضعیت حساب پیش از تأیید OTP افشا نمی‌شود.

پذیرش اعضای دعوت‌شده از `POST /api/auth/team-invitations/{id}/accept` با قرارداد قبلی است؛ ثبت‌نام سازمان تازه جای آن را نمی‌گیرد.

## خطاهای قرارداد

| وضعیت | code | رفتار فرانت |
|---|---|---|
|400|validation_failed، invalid_csrf یا invalid_registration_name|اصلاح فیلد/CSRF؛ OTP مصرف نشده|
|401|unauthorized|کد نادرست/منقضی/مصرف‌شده یا حساب غیرمجاز؛ قواعد قبلی|
|409|registration_required|پس از OTP معتبر، تکمیل فرم ثبت‌نام|
|409|mobile_already_registered|ثبت‌نام شماره موجود؛ ورود را پیشنهاد کنید؛ حساب و نشست عوض نمی‌شوند|
|409|email_unavailable|ایمیل دیگری وارد شود؛ حساب قبلی تغییر نمی‌کند|
|409|conflict|رقابت یکتایی در DB؛ بازخوانی/اصلاح و تلاش دوباره|
|409|team_invitation_pending|مسیر پذیرش صریح دعوت تیم|
|429|rate_limited|رعایت فاصله درخواست OTP|
|503|خطای ارسال OTP یا کاتالوگ trial|تلاش بعدی؛ ثبت‌نام ناقص commit نمی‌شود|

قفل advisory موبایل و قفل challenge فعلی بین ورود، ثبت‌نام و دعوت مشترک‌اند. رقابت ثبت‌نام همان شماره تنها یک حساب/هدیه می‌سازد. قید یکتایی normalizedEmail از ساخت دو سازمان با یک ایمیل جلوگیری می‌کند؛ شکست تراکنش، حساب/سازمان/هدیه/نشست ناقص باقی نمی‌گذارد.

## migration و اتصال فرانت

migration `20261017110941_SeparateRegistrationFromLogin` فقط ستون nullable `AspNetUsers.ReferralCode` با max64 اضافه می‌کند؛ حساب‌های قدیمی null باقی می‌مانند. Down با وجود کد ذخیره‌شده از حذف داده جلوگیری می‌کند. migration باید پیش از API جدید در تسک انتشار مستقل اعمال شود؛ در این کار فقط روی PostgreSQL اختصاصی تست اعمال شده است. SQL بازبینی در `artifacts/registration-split-migrations.sql` تولید می‌شود.

در Angular دو فرم/مسیر جدا بسازید: ورود فقط موبایل و کد؛ ثبت‌نام موبایل، ایمیل، نام، نام خانوادگی، کد معرف اختیاری و تأیید OTP. هر دو از request موجود استفاده کنند، اما submit ثبت‌نام باید register را صدا بزند. ثبت‌نام شماره موجود فرم را به ورود هدایت کند؛ در ورود شماره ناشناخته فرم ثبت‌نام باز شود. توکن/کد/کوکی در URL یا لاگ ثبت نشوند. دعوت تیم صفحه مستقل قبلی خود را حفظ کند. این مخزن تغییر فرانت ندارد.
