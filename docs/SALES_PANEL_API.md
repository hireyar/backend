# پنل فروش و پورسانت — قرارداد API

## اصلاح جستجو و خطای انتساب — 2026-10-21

`GET /api/sales/leads` و `GET /api/admin/sales/leads` پارامتر اختیاری `search` (حداکثر۲۰۰کاراکتر) دارند؛ فاصله ابتدا/انتها حذف می‌شود و تطبیق بخشی از `customerName` یا `mobile` پیش از شمارش و صفحه‌بندی انجام می‌شود. مقدار خالی/فقطفاصله فیلتر ندارد. search با status و agentId مدیریت ترکیب می‌شود؛ در پنل فروش، agentId ارسالی همچنان scope هویت سرور را عوض نمی‌کند.

اگر لید شماره به فروشنده دیگری منتسب باشد، `POST /api/sales/leads` با409 و `code=lead_already_claimed` و `title=این شماره توسط کارشناس فروش دیگری ثبت شده است` رد می‌شود؛ همین خطا حتی پس از خرید/فعال‌شدن اشتراک اولویت دارد. تکرار ثبت همان فروشنده/لید بدون فروشنده رفتار قبلی دارد.

طبق پاسخ نهایی کاربر، مشتری بدون انتساب دارای هدیه/تریال فعال یا اشتراک منقضی قابل افزودن است. فقط اشتراک پولی **مؤثر و فعال در اکنون** (از CurrentAsync موجود، با OrderId) مانع است:409، `code=customer_has_active_subscription` و `title=این شماره قبلا ثبت شده و اشتراک فعال دارد`. سفارش Pending یا اشتراک زمان‌بندی‌شده آینده به‌تنهایی اشتراک فعال نیست؛ override اداری و سفارش‌های excluded طبق قواعد سرویس جاری لحاظ می‌شوند. قفل موبایل سپس ردیف سازمان سپس قفل فروش، بررسی و ثبت را با تأیید خرید/اصلاح اشتراک سریالی می‌کند. هیچ حساب، هدیه یا اشتراک تازه‌ای از POST leads ساخته نمی‌شود.

شماره جدید با Waiting، مشتری صرفاً ثبت‌نام‌شده/هدیه/تریال بدون خرید تأییدشده با Registered و مشتری دارای سابقه خرید منقضی با Won وارد فهرست می‌شود؛ Won سابقه خرید است و وضعیت انقضای اشتراک نیست. افزودن مشتری به‌تنهایی پورسانت قبلی ایجاد نمی‌کند؛ تأیید خرید/تمدید بعدی با نرخ DB و snapshot فعلی، ردیف مستقل در «پورسانت من» می‌سازد. migration جدید لازم نیست. [پرامپت اصلاحات فرانت](SALES_CUSTOMER_FIXES_FRONTEND_PROMPT.md).

## تغییر ورود خصوصی فروش — 2026-10-20 / ADR-078

مسیر فرانت اکنون `/salesadmin/{randomkey}` است، مطابق درخواست صریح کاربر و ساختار ورودی سوپرادمین؛ **کپچا ندارد**. مسیر قدیمی /sales/login مرجع معتبر نیست و نباید در فرانت باقی بماند. بک‌اند این ریپو Angular را serve نمی‌کند؛ قرارداد guard و API آماده است و تغییر router در ریپوی فرانت انجام می‌شود.

تنظیمات مستقل `SalesAdmin` در appsettings.json: Enabled=false، RandomKey خالی، AccessMinutes=15 و AuthRequestsPerMinute=10. برای فعال‌سازی، Enabled=true و RandomKey واقعی۳۲تا۱۲۸کاراکتر از A-Z/a-z/0-9/_/- در appsettings محیطی خصوصی یا environment (SalesAdmin__Enabled و SalesAdmin__RandomKey) تنظیم شود؛ مقدار واقعی در Git، bundle عمومی یا log نباشد. عمر۱تا۳۰دقیقه و limiter۱تا۱۰۰۰ در دقیقه اعتبارسنجی می‌شوند. الگوی فایل tracked عمداً کلید واقعی ندارد.

`GET /api/sales/auth/entry` با **X-Sales-Entry** برگرفته از segment مسیر، پاسخ `{enabled:true}` می‌دهد؛ کلید نادرست/ناموجود/تکراری یا غیرفعال404. همان header روی POST login و GET me و POST logout اجباری است؛ SalesAuth یک فیلتر مشترک دارد. فرم login همچنان فقط `{mobile,password}` است؛ endpoint یا فیلد کپچا اضافه نشده است. X-Admin-Entry جایگزین کلید فروش نیست. مسیرهای داده فروش همان JWT مستقل Sales را می‌خواهند؛ fingerprint کلید جاری در token نیز بررسی می‌شود. تغییر کلید پس از اعمال تنظیمات/راه‌اندازی مجدد یا غیرفعال‌سازی، تمام نشست‌های فروش قدیمی را401 می‌کند؛ تنظیمات/نشست سوپرادمین مستقل می‌مانند. login/entry limiter مستقل sales-auth دارند. این تغییر schema/migration اضافی برای ورود لازم ندارد.

2026-10-20 / ADR-076. مرجع ظاهر: فایل HTML دو نمای فروشنده/سوپرادمین ارائه‌شده کاربر؛ متن و اسکریپت آن داده مرجع طراحی‌اند. اصلاح صریح کاربر برای فرم پورسانت و درخواست واریز بر نمونه مقدم است. کاربر صریحاً پورسانت را فقط برای خرید و تمدید **اشتراک** انتخاب کرد؛ خرید بسته مصاحبه پورسانت ندارد. Angular در ریپوی جداست.

## هویت و ثبت‌نام

فروشنده کارمند پلتفرم است و حسابش در SalesAgents مستقل از AspNetUsers، سازمان، Recruiter و سوپرادمین ذخیره می‌شود. حساب از سوپرادمین ساخته می‌شود؛ ثبت‌نام عمومی فروشنده نداریم. ورود موبایل ASCII `09xxxxxxxxx` و رمز ۱۲ تا ۱۲۸ کاراکتر، بدون کپچا و بدون X-Admin-Entry است. مسیر پیشنهادی فرانت `/salesadmin/{randomkey}`؛ نمای مدیریت داخل سوپرادمین موجود. سوییچ نمای HTML به معنی اعطای دسترسی نیست.

- `POST /api/sales/auth/login` با `{mobile,password}` → `{accessToken,expiresAtUtc}`؛ JWT مستقل Sales با audience پسوند `:sales`، عمر پیش‌فرض۱۵دقیقه (قابل تنظیم۱تا۳۰دقیقه)، بدون refresh/cookie؛ پس از انقضا ورود مجدد.
- `GET /api/sales/auth/me` → SalesAgentDto؛ `POST /api/sales/auth/logout` →204 و ابطال تمام نشست‌های همان فروشنده.
- هر درخواست، فعال‌بودن/قفل/مهر نشست را از DB بررسی می‌کند. پنج رمز نادرست هم‌زمان نیز حساب را۱۵دقیقه قفل و نشست قبلی را باطل می‌کنند؛ IP limiter موجود نیز برقرار است. reset/ویرایش ادمین نشست‌ها را باطل می‌کند. رمز اولیه/reset فقط در پاسخ همان عملیات برمی‌گردد؛ در log یا storage مرورگر نگه ندارید.
- ثبت‌نام **مشتری** همان `POST /api/auth/register` با OTP و مشخصات فعلی می‌ماند؛ هیچ agentId/organizationId/نقش/پورسانتی از مشتری پذیرفته نمی‌شود. در تراکنش ثبت‌نام شماره لید با شماره تأییدشده match و سازمان/تاریخ ثبت‌نام ثابت می‌شود. کد معرف قدیمی فقط داده ثبت‌نام است و جایگزین تطبیق موبایل نیست. هدیه موجود۴۸ساعت/۲مصاحبه بدون تغییر است؛ ورود و دعوت عضو هدیه/انتساب جدید نمی‌سازند.

## نمای فروشنده

همه مسیرهای زیر Bearer مستقل Sales، no-store و scope فروشنده احرازشده دارند. agentId query نمی‌تواند scope را تغییر دهد. رکورد متعلق به فروشنده دیگر404 است. Page پیش‌فرض۱، PageSize۲۰ و حداکثر۱۰۰.

| روش و مسیر /api/sales | ورودی/خروجی |
|---|---|
| GET dashboard | CallsLast30Days/Waiting/Registered/Won/Dead/CurrentMonthCommissionRial و PendingPayouts؛ ActiveAgents فقط مدیریت و در این نما صفر |
| GET leads | page/pageSize/status=Waiting\|Registered\|Won\|Dead/search → Page<SalesLeadDto> |
| POST leads | `{mobile,customerName,note}`؛ نامmax200 و note اختیاریmax2000 → SalesLeadDto |
| PUT leads/{id}/follow-up | `{note,followUpAtUtc}` →204؛ زمان nullable، ثبت تماس دوباره و بازگشت Dead به Waiting |
| GET commissions | page/pageSize/status و registeredFromUtc/registeredToUtc و leadId/payoutId اختیاری → SalesCommissionPage |
| GET payouts | page/pageSize → Page<SalesPayoutDto> |
| POST payouts | `{requestId,commissionIds:[...]}`، UUID غیرخالی و۱تا۱۰۰شناسه یکتا → SalesPayoutDto |

هر شماره فقط یک لید دارد و حذف نمی‌شود؛ اولین ثبت‌کننده برنده است، حتی برای لید Dead. تکرار409/lead_already_claimed و رخداد ثبت‌شده برای ادمین دارد؛ اطلاعات هویتی فروشنده دیگر افشا نمی‌شود. شماره مشتری Owner ازپیش‌ثبت‌شده هم قابل ادعاست اگر سازمانش مالک فروش نداشته و اشتراک پولی فعال نداشته باشد؛ هدیه/تریال فعال و اشتراک منقضی مانع نیستند و تاریخ ثبت‌نام واقعی او حفظ می‌شود. شماره عضو Recruiter قابل ادعا نیست. ثبت تماس جدید خرید قبلی را عطف‌به‌ماسبق پورسانت نمی‌دهد.

وضعیت لید: Waiting تا پیش از ثبت‌نام؛ Dead پس از۳۰روز از آخرین تماس بدون ثبت‌نام؛ Registered پس از ثبت‌نام بدون خرید اشتراک تأییدشده؛ Won پس از خرید اشتراک. وضعیت‌ها محاسبه می‌شوند، GET write ندارد. تماس دوباره لید ثبت‌نام‌شده یا خریدکرده وضعیت قطعی را عقب نمی‌برد. FollowUpAtUtc فقط یادآور در فهرست است؛ ارسال پیامک/اعلان خودکار اضافه نشده است.

## فرم پورسانت من و درخواست واریز

فیلتر `registeredFromUtc <= تاریخ ثبت‌نام مشتری < registeredToUtc` است، **نه تاریخ تماس، خرید یا تمدید**؛ هر دو کران اختیاری، UTC با Z و from<to. روز شمسی در فرانت به مرز UTC همان روز تهران تبدیل شود؛ برای شمول روز پایان، ابتدای روز بعد را بفرستید. تاریخ ثبت‌نام در هر ردیف پاسخ هست. فیلتر یک مشتری تمدیدهایش را هم شامل می‌شود، حتی اگر تمدید در ماه دیگری باشد.

`SalesCommissionPage` شامل `rows:{items,total,pageNumber,pageSize}`، `currency=IRR` و مجموع‌های `totalAmountRial,availableAmountRial,requestedAmountRial,paidAmountRial` است. مجموع‌ها روی **تمام نتایج فیلترشده** پیش از صفحه‌بندی‌اند. جدول هر ردیف: مشتری، تاریخ ثبت‌نام، نوع FirstSale/Renewal، مبلغ فاکتور، درصد، مبلغ پورسانت، تاریخ فروش، availableAtUtc، status، payoutId و canRequest. مبالغ DB/HTTP ریال صحیح‌اند؛ برای نمایش تومان فقط تقسیم بر۱۰ در فرانت.

اولین اشتراک **پولی تأییدشده سازمان** FirstSale و سفارش‌های اشتراک بعدی Renewal هستند. trial و هدیه تمدید پولی محسوب نمی‌شوند. ثبت سفارش Pending یا خرید بسته مصاحبه هیچ پورسانتی ندارد. تأیید سفارش موجود با پرداخت مرجع یکسان idempotent است. پیش‌فرض نرخ هر فروشنده۲۰٪/۵٪ است و تا دو رقم اعشار قابل تنظیم؛ مبلغ `floor(invoiceAmountRial * percent / 100)`، بر مبلغ واقعی سفارش پس از تخفیف محاسبه می‌شود. مبلغ و درصد همان زمان snapshot و immutable می‌شوند. نرخ صفر ردیف سابقه صفر دارد و قابل درخواست نیست. غیرفعال‌سازی، انتساب مادام‌العمر و سابقه را حذف نمی‌کند؛ ادمین می‌تواند انتساب آینده را با انتقال تغییر دهد.

چرخه مستقل هر سفارش:

`Holding` (۷روز از تأیید) → `Available` → با درخواست فروشنده `Requested` → تصمیم ادمین `Paid` یا `Returned`.

انتخاب فقط ردیف‌های canRequest=true. درخواست گروهی تماماً اتمیک است؛ یک ردیف نامعتبر/درخواست‌شده/در انتظار۷روز کل درخواست را409 می‌کند؛ شناسه خارج scope404 است. مرورگر requestId تازه را هنگام کلیک بسازد و در retry همان را با همان مجموعه شناسه‌ها بفرستد؛ پاسخ تکراری همان payout است. همان requestId با مجموعه دیگر409/idempotency_conflict. شناسه تکراری در یک درخواست400. دو درخواست متفاوت هم‌زمان روی یک ردیف فقط یک برنده دارند.

پس از درخواست، payoutId به ردیف وصل می‌ماند و با reload هم دوباره قابل انتخاب نیست. هیچ واریز بانکی خودکار انجام نمی‌شود؛ ادمین پس از انجام واقعی واریز، رسید/توضیح را ثبت و Paid می‌کند. Returned طبق شرط «دوباره درخواست ندهد تا تمدید» وضعیت نهایی همان دوره است و دوباره Available نمی‌شود. تمدید بعدی **ردیف تازه با همان مشتری** می‌سازد و پس از۷روز مستقل قابل درخواست است؛ ردیف قدیمی هرگز باز نمی‌شود. درخواست تسویه به فیلتر تاریخ اعتماد نمی‌کند، شناسه‌ها را سرور دوباره اعتبارسنجی می‌کند. نمونه HTML واریز ماهانه خودکار داشت؛ در این قرارداد اقدام فروشنده و تأیید ادمین مبناست و scheduler واریز نداریم.

## نمای سوپرادمین

Bearer فعلی SystemAdmin با کپچا و entry flow موجود؛ فروشنده/Owner/Recruiter به این مسیرها دسترسی ندارند.

| روش و مسیر /api/admin/sales | قرارداد |
|---|---|
| GET dashboard | آمار کل و تعداد نیروهای فعال/درخواست‌های منتظر |
| GET agents | page/pageSize → Page<SalesAgentDto> |
| POST agents | `{fullName,mobile,firstSalePercent:20,renewalPercent:5,isActive:true}` → `{agent,password}`؛ رمز تصادفی فقط همین پاسخ |
| PUT agents/{id} | همان فیلدها؛ تغییر درصد برای فروش آینده؛ ابطال نشست‌ها |
| POST agents/{id}/reset-password | رمز تصادفی تازه و ابطال نشست/قفل؛ `{agent,password}` |
| POST agents/{id}/transfer | `{targetAgentId,includeCustomers,reason}` → تعداد منتقل‌شده؛ مقصد فعال، مبدأ متفاوت |
| GET leads | page/pageSize/status/agentId/search اختیاری |
| GET commissions | همان فیلتر تاریخ ثبت‌نام/وضعیت/leadId/payoutId، agentId اختیاری |
| GET payouts | page/pageSize/agentId اختیاری |
| POST payouts/{id}/review | `{paid:true\|false,note}`؛ توضیح/مرجع رسیدmax1000 اجباری؛ نتیجه Paid یا Returned |
| GET audits | page/pageSize → Page<SalesAuditDto> |

انتقال پیش‌فرض فقط لیدهای هنوز ثبت‌نام‌نشده Waiting/Dead است؛ includeCustomers=true همه انتساب‌های منبع را به مقصد منتقل می‌کند. تاریخچه مبلغ، فروشنده پورسانت ثبت‌شده و درخواست‌های قبلی **منتقل یا بازنویسی نمی‌شوند**؛ تمدیدهای تأییدشده بعد از انتقال به مقصد تعلق دارند. دلیل و شناسه مبدأ/مقصد در audit DB ثبت می‌شوند. تغییر درصد، ایجاد/ویرایش/reset حساب، ادعای مشتری موجود، تکرار ردشده، پیگیری، ثبت‌نام، درخواست و نتیجه واریز نیز audit دارند؛ audit داده درخواست HTTP را در log عمومی منتشر نمی‌کند.

جزئیات ردیف‌های هر درخواست از GET commissions با payoutId همان درخواست خوانده می‌شود؛ جزئیات خرید/تمدید یک لید با leadId همان لید، با حفظ scope، قابل فیلتر است.

تأیید دوباره دقیق همان تصمیم و note روی payout همان نتیجه را می‌دهد؛ تصمیم متناقض409/payout_already_reviewed. رسید را بعد از ثبت نهایی با این API ویرایش نمی‌کنیم. اطلاعات حساب بانکی در این مرحله از HTML/درخواست کاربر تعیین نشده و API بانکی/ذخیره شماره کارت اضافه نشده است.

## migration و مرز انتشار

Migration `20261020121951_AddSalesPanel` پنج جدول جدید می‌سازد؛ حساب، لید، انتساب یا پورسانت تاریخی seed/backfill نمی‌کند. FK سازمان/سفارش و trigger deferred، منبع تأییدشده و مبلغ/مجموع درخواست را بررسی می‌کنند؛ history و audit غیرقابل حذف/بازنویسی‌اند. Down دارای داده رد می‌شود و backup لازم است. قفل transaction-level کوتاه PostgreSQL عملیات این ماژول کوچک را سریالی می‌کند؛ موبایل/سازمان قبل از قفل فروش گرفته می‌شوند، I/O شبکه زیر قفل نداریم. هیچ Repository عمومی یا زیرساخت توزیع‌شده اضافه نشده است.

پیش از نسخه API، migration باید در مقصد اعمال شود؛ این تسک آن را فقط روی PostgreSQL آزمایشی محلی اجرا می‌کند. push/deploy/production و Angular در این تغییر اجرا نمی‌شوند. قرارداد اتصال رابط: [SALES_PANEL_FRONTEND_PROMPT](SALES_PANEL_FRONTEND_PROMPT.md).
