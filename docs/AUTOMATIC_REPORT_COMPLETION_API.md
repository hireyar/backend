# تکمیل خودکار شاخص‌ها و روایت گزارش — 2026-10-17

این قرارداد، تولید صرفاً دستی روایت در ADR-060 و REPORT_COMPLETION_API را برای مصاحبه‌هایی که از این پس تکمیل می‌شوند اصلاح می‌کند. مسیرهای دستی Owner، scope سازمان، شواهد معتبر، سقف تلاش مستقل و GET بدون AI/write حفظ‌اند.

هر مسیر domain Complete (دستی یا پایان خودکار مصاحبه) مقدار AutomaticReportCompletionEnabled را true می‌کند. migration افزایشی 20261017093755_AutomateFutureReportCompletion برای تمام رکوردهای موجود false می‌گذارد؛ مصاحبه‌های تاریخی صرفاً با ارتقا یا restart به AI ارسال نمی‌شوند. لغو جلسه opt-in نمی‌کند. این migration باید پیش از API جدید اعمال شود؛ در این تغییر به مقصد اعمال نشده است.

worker موجود AnswerAssessmentWorker، با همان فلگ AnswerAssessments:WorkerEnabled، پس از نوبت ارزیابی پاسخ‌ها، حداکثر سه جلسه opt-in را در هر نوبت به‌صورت چرخشی بررسی می‌کند. بعد از restart، markerهای ماندگار و lease/cache مانع فراموشی کار یا درخواست تکراری موفق می‌شوند. صف، سرویس توزیع‌شده یا provider تازه اضافه نشده است.

ترتیب کار:

1. پایان ارزیابی‌های اولیه؛ Queued/Processing/RecoveryPending مانع روایت نهایی‌اند.
2. بازیابی شاخص‌های missing/invalid قابل‌ترمیم با حداکثر سه تلاش مستقل هر پاسخ. نمره، شاهد و بودجه ارزیابی موفق دست‌نخورده‌اند؛ شاخص موفق و explicit insufficient_evidence بازنویسی نمی‌شوند. همسویی بدون JD تولید نمی‌شود.
3. پس از پایان یا اتمام بودجه بازیابی، تولید روایت با provider/model پیکربندی‌شده فعلی گزارش. sourceId/نقل‌قول، hash، timeout، lease و fencing قبلی مشترک‌اند. شکست شاخص یا روایت نمره‌های معتبر را حذف نمی‌کند. روایت نامعتبر، timeout یا شکست provider پس از حداکثر سه تلاش همان input متوقف و failureCode نمایش داده می‌شود.

تولید خودکار از سازمان همان session در worker استفاده می‌کند و هویت ساختگی Owner نمی‌سازد. endpointهای دستی همچنان Owner-only هستند؛ Recruiter فقط می‌خواند. GET گزارش، خروجی چاپ و GET فهرست، تولید یا بازیابی را آغاز نمی‌کنند. فراخوانی provider بیرون قفل سازمان انجام می‌شود. تغییر داده/نسخه باعث fence یا cache ورودی جدید می‌شود؛ تصمیم انسانی با تولید روایت ممکن است نیازمند بازبینی شود و خودکار بازنویسی نمی‌شود.

processing.shouldPoll و pollAfterSeconds اکنون تا پایان بازیابی/روایت نیز معتبرند، حتی وقتی pendingAssessments صفر است. Worker خاموش → Paused و shouldPoll=false؛ اتمام بودجه یا کمبود صریح شاهد → توقف polling، failure و null واقعی در جزئیات. این readiness برای Owner/Recruiter مشترک است؛ حق retry/generate فقط Owner می‌ماند. Angular می‌تواند همان polling عمومی قبلی را ادامه دهد و برای جلسات opt-in نیازی به POST خودکار مرورگر ندارد.

تشخیص خواندنی یک گزارش تاریخی نشان داد هر۱۰پاسخ evaluatorVersion=answer-quality/1، DimensionsJson خالی و بدون رکورد روایت دارند؛ علت null، داده legacy است، نه صفر بودن عملکرد یا خرابی نمایش. شناسه یا متن واقعی کارجو در Git ثبت نشده است. این تشخیص اثبات ترمیم گزارش مقصد نیست. ترمیم موردی تاریخی از مسیرهای صریح Owner موجود انجام می‌شود؛ اجرای آن روی داده واقعی و ارسال مجدد به provider در این تغییر انجام نشده است.
